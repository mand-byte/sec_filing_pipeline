# Repository-Wide Documentation Boundary Audit Design

## 目标
对当前仓库的主文档体系做一次**只报告问题、不自动修改**的边界巡检，输出一份结构化问题清单。巡检重点不是继续改文档，而是判断在最近一轮整理之后，仓库里还剩哪些命名不一致、边界模糊、过时引用、临时视图污染、以及后续可选清理项。

## 背景
当前主文档体系已经基本成型：

- `DEMANDS.md` — 总架构 / 总需求文档
- `EXTRACTION_METHOD.md` — 抽取方法主文档
- `EXTRACTION_FIELDS.md` — 字段字典主文档
- `GOLDEN_SET.md` — truth / evaluation 主文档

最近我们已经完成多轮收敛，但仓库里仍可能存在：
- 历史命名遗留
- spec / plan / worktree 残留带来的“看起来像重复”的内容
- 字段定义与方法定义之间的轻微边界漂移
- 文档间引用路径仍不够理想的问题

用户这次要求的是**报告**，不是继续自动清理。

## 设计目标
这次巡检输出必须满足：

- 只报告，不修改文件。
- 面向当前仓库状态，而不是历史状态。
- 以“问题清单”形式输出，而不是泛泛而谈。
- 每条问题都说明：
  - 问题类型
  - 具体位置
  - 为什么算问题
  - 影响范围
  - 是否建议处理
  - 推荐动作

## 非目标
本次不做：

- 不自动编辑任何文档
- 不创建新的主文档
- 不重新设计主文档体系
- 不处理 `.claude/worktrees/**` 内的临时内容本身，只把它视为审计时需要识别的噪声来源

## 推荐输出结构
建议最终输出采用以下 5 类结构：

### 1. 命名不一致
关注：
- 文件名本身是否可疑（例如 `EXTRACTION_FIELDS.md` 是否像历史 typo）
- 文档内部的 route / field / form_family 命名是否和其他主文档不一致
- 同一概念是否在不同文档中有多个名称

### 2. 边界模糊
关注：
- `DEMANDS.md` 是否仍残留过多方法细节或评估细节
- `EXTRACTION_METHOD.md` 是否仍残留字段字典职责或 truth/eval 职责
- `EXTRACTION_FIELDS.md` 是否仍残留方法论或评估论
- `GOLDEN_SET.md` 是否仍残留过多实现方法细节

### 3. 过时引用
关注：
- 根目录正式文档是否还引用已删除或已退役文档
- 是否存在应该指向 authority doc 却还指向旧文档或计划文档的情况
- 是否存在 spec/plan 中的引用对正式文档有误导性（只报告，不要求本轮处理）

### 4. 临时视图污染
关注：
- `.claude/worktrees/**` 中的历史文档是否会影响 grep / glob /人工阅读
- spec / plan 文档中的旧引用是否属于正常历史记录，还是会对仓库使用者造成困扰
- `.pytest_cache/README.md` 这类非正式文档是否会干扰文档检索结果

### 5. 可选清理项
这部分不是“必须修”，而是“如果继续打磨文档体系，下一步最值得做什么”。

## 巡检范围
正式主文档优先：
- `DEMANDS.md`
- `EXTRACTION_METHOD.md`
- `EXTRACTION_FIELDS.md`
- `GOLDEN_SET.md`

附加噪声源与上下文：
- `docs/superpowers/specs/*.md`
- `docs/superpowers/plans/*.md`
- `.claude/worktrees/**/*.md`
- `.pytest_cache/README.md`

## 输出要求
最终报告应：
- 尽量短，但有判断力
- 优先列真正会影响后续维护的项
- 区分“正式文档问题”和“审计噪声问题”
- 不把 spec/plan 历史引用误报成正式文档错误

## 实施验收标准
完成后应满足：
- 报告能帮助用户快速知道“还剩哪些文档边界问题”
- 报告不会把已经有意保留的 spec/plan 内容误判成正式文档错误
- 报告不会掺杂自动修改建议以外的执行动作
- 用户看完后能直接决定下一轮要不要继续清理
